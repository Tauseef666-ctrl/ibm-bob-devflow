## The state problem, and how it was solved

`analysisStore` is module-level memory. Each Vercel invocation may get a fresh
instance, so `GET /api/analysis/:id/status` returned `{"error":"Session not
found"}` on a cold start. The failure was **flaky, not consistent** — logs showed
one session polled successfully ~73s across many invocations, then a new one lost
its session 3s after starting. A warm instance hides the bug, which makes it a
bad demo-day failure mode.

Options considered:

| Option | Verdict |
|---|---|
| **A. Stateless re-run fallback** — on a store miss, re-run the analysis. | Rejected: re-runs the workflow per request, so cost goes up, and `remediate`/`reanalyze` stay unreliable anyway. |
| **B. Single synchronous endpoint** — `POST /api/analysis/run` returns findings + action plan + report in one response. | **Chosen.** Cleanest serverless semantics, and the workflow takes under a second, so there is nothing to gain from streaming. |
| **C. External store** (Upstash Redis / Vercel KV). | Rejected: contradicts the documented "no database" decision, and needs infra for a demo. |

What B actually involved:

- `backend/src/routes/analysis.js` — added `POST /api/analysis/run`. `IS_SERVERLESS`
  is derived from `process.env.VERCEL`.
- `backend/src/server.js` — `/api/health` now returns `"stateful": false` in
  production.
- `frontend/src/api/client.js` — `isStateful()` reads that flag once and caches
  it. `startOrRun`, `runAnalysis`, and `getStatusAny` / `getFindingsAny` /
  `getActionPlanAny` / `getReportAny` / `reanalyzeAny` / `remediateAny` wrap both
  paths. Results are cached in `sessionStorage` under `devflow:run:<id>` so the
  five pages can each read what they need.
- The five page files were switched to the `*Any` variants. All 13 call sites.

Local behaviour is unchanged: `npm start` still uses the async start/poll flow,
because the in-memory store works there.

**Cost of the decision:** the parent/child comparison in the report, and
auto-remediation, both need a persistent store and a writable filesystem, so
both are local-only. The UI states this rather than failing.

## Bugs fixed this session

### 1. The "500 on /api/analysis/start" was our own bug, not a serverless one

PowerShell was stripping quotes from inline JSON, so the server received
`{projectId:items-api}` instead of `{"projectId":"items-api"}`. Sent from a file
it returns 202 and runs. Two earlier theories were also wrong: `uuid`/ESM
(these projects run Node 24, which handles `require(ESM)`), and "read-only FS
makes analysis impossible".

**Pass JSON from a file in PowerShell.** Inline JSON loses its quotes.

### 2. Findings gap: 18 on Vercel vs 21 locally

Diffing both runs identified two independent causes:

- `vercel.json` shipped no non-JS files, so `documentation.js:22`
  (`fs.existsSync` on README.md) saw no README and *inverted* its findings.
  Fixed with `"includeFiles": "sample-project/**"`.
- `buildRelease.js:81` returns early when `npm install` fails. On Vercel the
  install cannot succeed (read-only bundle, no registry access), so it emitted
  a false critical **and suppressed the real `npm test failed` finding**. Fixed
  by skipping install when `process.env.VERCEL` is set; `npm test` still runs.

Vercel had `README.md is missing` and `npm install failed`; local had
`readme-no-setup`, `missing-env-docs` ×2, `No CHANGELOG found`, `npm test failed`.

### 3. Build failure cause

Both failing deployments carried:
`Invalid vercel.json - functions['api/index.js'].includeFiles' should be string`
`includeFiles` takes a **string**, not an array. Reproduced locally with
`npx vercel build`, which is much faster than waiting on a remote build.

### 4. `maxDuration` stays at 30s

Raising it to 300 was rejected on this plan. It is not needed — the workflow
finishes in well under two seconds.

### 5. UI text was mangled in all five pages

A refactor applied its renames with PowerShell `-replace` piped to
`Set-Content`. That decoded the files as single-byte text and re-encoded every
multi-byte character, so em dashes and ellipses rendered as garbage on the live
site. Restored from `9b908bc` and reapplied with Node, which round-trips UTF-8.
`.gitattributes` was added to normalise line endings.

**Never bulk-rewrite source through PowerShell `Get-Content` / `Set-Content`.**
Use the edit tool, or Node with explicit `utf8` on both read and write.

  inspection only. This is the largest remaining gap and it is a real one.
