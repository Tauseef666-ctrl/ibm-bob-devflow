## Fixed this session

### 1. The "500 on /api/analysis/start" was our own bug, not a serverless one

PowerShell was stripping quotes from inline JSON, so the server received
`{projectId:items-api}` instead of `{"projectId":"items-api"}`. Sent from a file
it returns 202 and runs. Two earlier theories were also wrong: `uuid`/ESM
(these projects run Node 24, which handles `require(ESM)`), and "read-only FS
makes analysis impossible".

### 2. Findings gap: 18 on Vercel vs 21 locally

Diffing both runs identified two independent causes:

- `vercel.json` shipped no non-JS files, so `documentation.js:22`
  (`fs.existsSync` on README.md) saw no README and *inverted* its findings.
  Fixed with `"includeFiles": "sample-project/**"`.
- `buildRelease.js:81` returns early when `npm install` fails. On Vercel the
  install cannot succeed (read-only bundle, no registry access), so it emitted
  a false critical **and suppressed the real `npm test failed` finding**. Fixed
  by skipping install when `process.env.VERCEL` is set; `npm test` still runs.

Vercel had `README.md is missing` and `npm install failed`; local had
`readme-no-setup`, `missing-env-docs` ×2, `No CHANGELOG found`, `npm test failed`.

### 3. Build failure cause

Both failing deployments carried:
`Invalid vercel.json - functions['api/index.js'].includeFiles' should be string`
`includeFiles` takes a **string**, not an array. Reproduced locally with
`npx vercel build`, which is much faster than waiting on a remote build.

### 4. `maxDuration` stays at 30s

Raising it to 300 was rejected on this plan. It is not needed: the 202 response
returns before the orchestrator finishes, so the analysis never consumes the
function's request budget.

Local behaviour is unchanged and verified: 21 findings, 2/6/6/6/1, 9/9 tests.

## OPEN: in-memory store does not survive serverless invocations

This is the real blocker and it is architectural.

`analysisStore` is module-level memory. Each Vercel invocation may get a fresh
instance, so `GET /api/analysis/:id/status` returns `{"error":"Session not
found"}` on a cold start. The failure is **flaky, not consistent** — logs show
one session polled successfully ~73s across many invocations, then a new one
lost its session 3s after starting. A warm instance hides the bug, which makes
it a bad demo-day failure mode.

The frontend is built around this: `startAnalysis` then polls `status`,
`findings`, `action-plan` and `report` by session id, plus `remediate` and
`reanalyze` (`frontend/src/api/client.js:39-66`).

`AGENTS.md` records "no database — in-memory store sufficient", which is true
for a single-machine demo and false for a stateless deployment. This needs a
decision, not a patch.

### Options

| Option | Effort | Trade-off |
|---|---|---|
| **A. Stateless re-run fallback** — on a store miss, re-run the analysis; the analysis is deterministic, so any endpoint can rebuild its own result. Session id becomes self-describing. No frontend change. | Small, backend only | Re-runs the analysis per request, so compute cost goes up |
| **B. Single synchronous endpoint** — `POST /api/analysis/run` returns findings + action plan + report in one response; frontend stops polling. | Larger, touches the frontend contract | Cleanest serverless semantics; longest single request |
| **C. External store** (Upstash Redis / Vercel KV) — real persistence. | Medium, needs env vars and infra | Contradicts the documented "no database" decision |

A also makes `remediate` and `reanalyze` unreliable on Vercel regardless, since
the filesystem is read-only; those two need their own treatment either way.
